# 日记升级计划：从「写日记」到「记碎片，让 AI 整理」

> 参考 [memex-lab/memex](https://github.com/memex-lab/memex)（Flutter，**GPL-3.0**）
> 和 [celerforge/freenote](https://github.com/celerforge/freenote)（TypeScript，**AGPL-3.0**）。
>
> **两个都是传染性许可，所以规矩跟之前一样：只学设计，自己写实现，代码一行不抄。**
> 本文只记录「读到了什么想法」和「克克这边打算怎么做」，不含对方任何代码。
> 实际读过的：memex 的 `README`、`docs/agent_overview.en.md`、`docs/core_agent_design.en.md`
> 三份**设计文档**，以及 freenote 的 `src/lib/db/schema/*.ts`（4 个类型声明）。

---

## 0. 先说结论：不要把克克变成 memex

memex 的定位是**个人知识库**（PARA、PKM、日程聚合、自定义 agent 平台）。
克克的定位是**陪伴**。这两件事的取舍经常是相反的：
知识库要「全、准、可检索」，陪伴要「克制、有分寸、不像产品」。

所以这份计划是**挑着拿**的：

| 拿 | 不拿 |
|---|---|
| 碎片捕捉（不逼你写成篇） | P.A.R.A. / PKM 知识体系 |
| 碎片 → 结构化卡片 | 日程聚合（克克已经接了系统日历/提醒/闹钟） |
| **「要不要开口」是一个显式决策** | 自定义 agent 平台（克克的扩展口是 MCP） |
| 澄清提问 → 长期记忆 | 多角色抢着评论 |
| 洞察卡片（带证据） | 17 种卡片类型（收到 7 种） |
| Markdown 归档 | |

memex 最值得抄的其实不是任何一个功能，是**一句话**：

> "Not for writing daily entries — for capturing life in fragments and letting AI organize them."

克克现在的日记要求你**坐下来写一段话**。这是它用得少的根本原因。

## 1. 克克这边已经有的地基

这份计划之所以不算大工程，是因为一多半零件已经在了：

| 已有 | 位置 | 这次能直接用在哪 |
|---|---|---|
| Vision OCR + 场景标签（本地，不花钱） | `Attachments.describeImageLocally` | 第 2 项：媒体理解，几乎不用写新东西 |
| 语音转文字 | `VoiceCallService`（Speech 框架） | 第 1 项：语音碎片 |
| FTS5 **trigram** 分词 + bm25 | `MemoryDatabase` | 第 9 项：中文其实已经能搜（trigram 不挑语种），缺的是停用词和查询侧优化 |
| 统一 `Tool` 协议 + 编排层 | `Services/Orchestration/` | 第 4、6、7 项的 agent 都挂在这条链上 |
| 按任务配模型 | `SubModelConfig` | 卡片生成可以用便宜模型，评论用好模型 |
| 失败必须留痕 | `ErrorLog` + `GenerationFallback` | 第 4 项的兜底判据 |
| 记忆四选一（新增/合并/冲突/跳过）+ 水位线 | `MemorySmartAdd` / `MemoryService` | 第 7 项澄清答案入库 |
| **到期任务在打开时才处理**的惰性时序 | `MomentsStore.checkPendingReactions` | 第 5 项流水线的雏形，思路直接沿用 |
| 备份导出 | `BackupService` | 第 10 项 Markdown 归档 |
| 日记的分享 / 偷看 / 评论 | `DiaryEntry` | **保留不动**，这是克克独有的关系戏，memex 没有 |

## 2. 计划表

规模按「一个人一次能不能做完」估：**S** ≈ 半天，**M** ≈ 一到两天，**L** ≈ 三天以上。

### 第一阶段 · 碎片捕捉（观念转变，最核心）

| # | 事项 | 学自 | 为什么值得 | 依赖 | 规模 |
|---|---|---|---|---|---|
| 1 | **`Fragment` 模型 + 捕捉入口**。一条碎片 = 文字 / 图 / 语音 + 时间 +（可选）位置。日记页变成两层：上面是碎片流，下面是成篇的日记。**`DiaryEntry` 一个字段都不动。** | memex 的核心命题 | 现在的日记要求写成篇，所以没人写。碎片的门槛是「随手扔一句」 | — | M |
| 2 | **媒体理解**。图片走 EXIF 时间/GPS + 已有的 Vision OCR 和场景标签；语音走已有的 Speech 转写。**必须排在卡片生成前面**——卡片要读它的结果。 | memex `analyze_assets`（它是整条流水线的第一环，别的 agent 都 `dependsOn` 它） | 全本地、不花钱、不上传。跟「数据留在设备上」这条对得上 | 1 | S |

### 第二阶段 · 碎片 → 卡片

| # | 事项 | 学自 | 为什么值得 | 依赖 | 规模 |
|---|---|---|---|---|---|
| 3 | **`TimelineCard` 模型 + 卡片类型收敛到 7 种**：事件 / 待办 / 打卡 / 摘录 / 人与地点 / 数值 / 相册。（memex 有 17 种，对克克是负担——类型越多，模型越容易选错、越容易生成空字段，它自己在风险栏里也这么写） | memex 卡片分类，砍掉一半 | 结构化之后才谈得上洞察和检索 | 1 | M |
| 4 | **`CardGenerator`：只干一件事的 agent**，工具只有一个 `save_timeline_card`。<br>**完成判据**：保存工具调用成功 + 卡片确实落盘 + 类型合法 + 标题非空，四条缺一即失败。<br>**规则兜底**：没配 API / 调用失败时，用关键词规则出一张最朴素的「事件卡」，**绝不丢掉用户的输入**，同时进 `ErrorLog` 说明原因。 | memex `CardAgent` 的 `CardRunCompletionEvidence` 和 `rule_based_card_matcher` | 「一个 agent 只有一个职责」是 memex 整套设计里最扎实的一条。兜底那条跟克克已经定下的「兜底文案由用户 prompt 生成，生成不出来就说原因」是同一条线 | 2、3 | M |
| 5 | **`DiaryPipeline`：任务落盘、可断点续跑**。媒体分析 → 卡片 → 评论是串起来的几十秒，iOS 随时可能把 App 挂起。沿用朋友圈那套「到期任务在打开/回前台时处理」，加上依赖顺序和重试上限。 | memex `LocalTaskExecutor`（持久化 + 依赖 + 重试 + 串行化） | 链路一变长，不落盘就必丢。这一项做晚了，前面几项的体验会莫名其妙地坏 | 2、4 | L |

### 第三阶段 · 她的反应（这是克克的护城河）

| # | 事项 | 学自 | 为什么值得 | 依赖 | 规模 |
|---|---|---|---|---|---|
| 6 | **让她有权不说话**。评论 agent 必须显式调用 `save_comment` 或 `skip_comment` 其中一个才算结束，两个都直接终止本轮。 | memex `CommentAgent` 的双完成工具 | **这是整份清单里我最想要的一条。** 现在克克是「一定要说点什么」，结果就是废话。有权沉默，说出来的那句才值钱 | 4 | S |
| 7 | **澄清提问**。碎片里出现高价值歧义时，问一句、**只问一句**、尽量能一键回答。答案过一遍 gatekeeper，够格才写进长期记忆。<br>**打扰预算**：每天最多 N 条 + `dedupe_key` 去重。 | memex `AskClarificationAgent` / `ClarificationResolutionAgent`；它自己把「问太多毁掉记录体验」列为首要风险，这个教训直接抄 | 对陪伴类 App 来说，「她真的在关心细节」比任何整理功能都值钱。而且天然接上克克已有的 `MemorySmartAdd` 四选一 | 4、6 | M |

### 第四阶段 · 洞察

| # | 事项 | 学自 | 为什么值得 | 依赖 | 规模 |
|---|---|---|---|---|---|
| 8 | **洞察卡片**：趋势 / 对比 / 汇总 / 地图 / 时间线 / 相册。<br>**手动 + 定期触发，不是每条碎片都算**（全量分析很贵）。<br>**增量优先**：只看水位线之后的新卡片。<br>**每条洞察必须挂证据**——它依据了哪几张卡片，点得进去。 | memex `KnowledgeInsightAgent`；它把「小样本过度推断」列为风险，而证据链是唯一的解药 | 「你这个月睡得比上个月晚 40 分钟」这种话，只有攒够数据才说得出来 | 3、5 | L |

### 第五阶段 · 找得回来 / 带得走

| # | 事项 | 学自 | 为什么值得 | 依赖 | 规模 |
|---|---|---|---|---|---|
| 9 | **语义检索**。现在是 FTS5 trigram + bm25，**中文其实搜得到**（trigram 不挑语种），缺的是同义、近义和长句召回。加一层 embedding：按**结构**切块（标题/段落，不是定长），`embeddingUpdatedAt` 当水位线只重算变过的。 | freenote 的 `Note.embeddingUpdatedAt` 水位线 + 按 Markdown 标题切块 | 「上次说想去的那家店叫什么」——这种问题 bm25 答不了 | 3 | M |
| 10 | **Markdown 归档导出**。日记、碎片、卡片一键导出成互相链接的 `.md`。 | memex 的论点，值得原样接受：只有最朴素的文本能跨越时间；也是「随时能走」的承诺 | 克克已有 `BackupService`，加一个 Markdown 导出器即可 | 3 | S |

## 3. 建议的开工顺序

不要按阶段顺序做。**先打通一条最短的链路，让它能跑**：

```
1 碎片捕捉  →  2 媒体理解  →  4 卡片生成  →  6 她开口或不开口
```

这四项（M + S + M + S）跑通，日记就已经是个新东西了：
随手扔一句话或一张图，它变成一张卡片，她**可能**说一句，也可能什么都不说。

然后：

- **5（任务落盘）**在链路变长之后必须补，不然 iOS 挂起就丢，而且丢得没有规律，很难查
- **3（卡片类型）**可以先只做「事件」一种，第 4 项跑通之后再扩
- **7（澄清提问）**建议在有一周真实数据之后再开，否则调不出「什么算高价值歧义」
- **8、9** 放最后：都贵，而且依赖数据量，早做等于白做

## 4. 明确不做的，和原因

| 不做 | 原因 |
|---|---|
| P.A.R.A. / PKM 知识体系 | 克克不是知识库。用户来这儿不是为了归档资料 |
| 日程聚合 agent | 已经接了系统日历 / 提醒 / 闹钟，再做一套是重复且更差 |
| 自定义 agent 平台 | 克克的用户扩展口已经定成 MCP 了，两套扩展机制会互相打架 |
| 多角色评论 | 克克是一对一的关系。几个角色抢着在你日记下面留言会直接毁掉亲密感 |
| 卡片用 LLM 现生成 HTML/UI | memex 走的是动态 UI 那条路。SwiftUI 这边原生渲染又快又稳，没必要为了灵活性把渲染交给模型 |

## 5. 一个前置条件

这份计划的第 4、6、7 项都要往 system prompt 里加新的输出约定。
**在此之前必须先在 Xcode 里编译一次**——目前分支上约 5500 行、20 个提交从未编译过。
在没编译过的代码上叠新的 prompt 协议，出了问题分不清是编译期的还是模型的。
