## 30 秒结论

克克是一个 **SwiftUI iOS 陪伴 App**，部署目标 iOS 16.1。

- **人设完全由用户自己写**，App 不内置任何角色描述（这是硬规矩，见下）
- 支持 **6 家内置 AI 供应商 + 自定义供应商**，**每个角色可以挂在不同的供应商/模型上**
- 聊天之外还有：记忆、朋友圈、日记、经期、闹钟、书、游戏、画画、语音通话、番茄钟…
- 工具能力有三个来源：**内置模块**、**用户自己加的 MCP 服务器**、**外部搜索服务**，
  最后汇成一份统一的工具清单给模型

## 三条不能破的规矩

改任何代码之前先记住这三条。它们不是风格偏好，是踩过坑之后定下来的。

### 1. App 不替角色说话

人设由用户自己写。**不要**在代码里写任何「角色会说的话」——
不要内置人设、不要写兜底台词、不要在提示词里规定「符合温柔嘴硬的性格」或「可以带 *动作*」。

生成失败时显示**失败原因**（`GenerationFallback`），不要编一句话糊过去。
编的那句话会被存进游戏战绩、日记、聊天记录，看起来像角色真说过；
更糟的是它把失败藏起来了——Key 填错了用户还以为一切正常。

### 2. trace / 状态文案绝不进 messages

`ChatMessage.kind == .systemNote` 的消息**结构上就进不去上下文**：
`modelPayload` 对它返回 `nil`，而 `ClaudeService.send()` 收的是 `[ChatMessage.Payload]`——
`Payload` 里根本没有 trace 字段。发错东西是**编译错误**，不是 bug。

> 为什么这么严：状态文案曾经每轮都在发给模型，模型看多了会学着自己编报错、编工具调用。
> 想验证的话开「设置 → 报错记录 → 请求日志」，能看到每次实际发出去的完整 payload。

### 3. 密钥只进 Keychain

所有 API Key、MCP 的请求头、自定义供应商的请求头——全部走 `APIKeyStore`，
**不进 UserDefaults**。备份导出那边还有第二道按名字过滤的防线（`BackupService`）。

## 分层

```
Views (48)          SwiftUI 界面
   ↓ @EnvironmentObject
Services (58)       状态 + 业务逻辑，绝大多数是 @MainActor ObservableObject
   ↓
Models (8)          纯数据结构，Codable
```

数据都存在 **Documents 目录**：聊天是 `<personaId>_chat.jsonl`（一行一条，追加写），
记忆是 SQLite，其余是 JSON。没有 CoreData。

## 核心链路：一条消息是怎么发出去的

```
ChatStore.send(text)
  → OnDeviceRouter.decide()          端上路由，150ms 超时，不可用就直连
  → 组装 extraContext                记忆块 + 世界书 + 设备状态 + 时间
  → payloadForRequest                正则(非visualOnly) → 调教流水线 → 合并同角色
  → ContextCompressor                超过阈值就把老消息压成摘要
  → ClaudeService.send()
       ├ 挂工具：内置 MCP + 远端 MCP + 搜索
       ├ 流式 / 非流式（流式失败会自动退回非流式一次）
       ├ 工具循环，最多 4 轮，跑满后再来一轮**不带工具**逼它说话
       └ APIRetry：429/5xx/网络 退避重试
  → 回来：splitChoices → 存 ChatMessage（含 usage / 耗时 / 模型）
```

失败时：`APIFailure` 分 11 类给出人话原因 → 进 `ErrorLog` → 界面显示。

## 各领域一页纸

### 聊天与模型

| 文件 | 干什么 |
|---|---|
| `ChatStore.swift` | 最核心的一个。每个角色一个实例，管消息、设置、发送流程 |
| `ClaudeService.swift` | 所有供应商的请求出口。Claude 走 Messages API，其余走 OpenAI 兼容 |
| `StreamDecoding.swift` | SSE 分帧 + 两家的流式解码器。纯逻辑，不碰网络 |
| `ContextCompressor.swift` | 滚动摘要压缩。纯逻辑，超上下文时二分重试 |
| `APIFailure.swift` | 错误分类 + 退避重试策略 |
| `PersonaTuning.swift` | 按深度注入、正则、世界书、预设开场。**全是纯函数** |
| `Providers.swift` | 供应商定义、模型能力矩阵（哪些模型不认 temperature） |

### 工具（`Services/Orchestration/`）

```
Tool.swift              统一协议，三个来源都实现它
ToolResultEnvelope      工具结果进上下文的唯一出口，外部数据会被明确标记
MCP/                    用户自己加的 MCP 服务器（两种传输 + 状态 + 重连 + 逐工具开关）
Search/                 六家搜索服务的适配器
RouteDecision/OnDeviceRouter  端上路由（iOS 26 才有，条件编译）
```

### 记忆
`MemoryService.swift` + `MemoryDatabase.swift`（SQLite）。定期提炼 + 相关度检索。
**这块是目前最值得升级的**——见 `reference-rikkahub-jude-and-kelivo.md` §4。

### 排查工具（出问题先看这两个）
- `ErrorLog.swift` → 设置 → 报错记录。**所有报错都汇到这里**，能整份复制
- `RequestLog.swift` → 设置 → 请求日志。看每次**实际发出去了什么**，默认关

## 改代码时的坑（都踩过）

| 坑 | 后果 |
|---|---|
| `Localization.swift` 加了重复键 | **运行时崩溃**，不是编译错误 |
| `SettingsView` 的 `Group` 超过 10 个子视图 | 编译不过。拆成多个 `Group` |
| 在 `guard` / `if` 条件里用尾随闭包 | 编译不过。用显式闭包实参 |
| `@MainActor` 类的静态成员被非隔离上下文调用 | 编译不过。纯函数标 `nonisolated` |
| 用 `isLetter` 过滤标识符 | 它对中文返回 true，会生成非法的 API 函数名 |
| 用 `hashValue` 做稳定标识 | 每次启动加的盐不同。要稳定就自己写 FNV-1a |
| 忘了改 `project.pbxproj` | 新文件不参与编译，报"找不到类型" |

### 加新文件必须改 pbxproj 四处

`objectVersion = 56`，老式格式，Xcode 不在场只能手改：

1. `PBXBuildFile`：`B7F… /* X.swift in Sources */ = {… fileRef = F7F… };`
2. `PBXFileReference`：`F7F… /* X.swift */ = {… path = X.swift; …};`（子目录要带相对路径）
3. 所属 group 的 `children` 里加 `F7F…`
4. `PBXSourcesBuildPhase` 的 `files` 里加 `B7F…`

## 没有测试，怎么验证

仓库里**没有单元测试**，开发容器里也没有 Swift 工具链。目前的做法：

1. **全量括号配平**——先剥掉字符串和注释，再数 `(){}[]`
2. **纯算法用 Python 对拍**——把 Swift 逻辑照抄成 Python，造边界用例跑
   （Markdown 分块、上下文切分、退避策略、工具循环、调教流水线、MCP 协议…都这么验过）
3. **本地化重复键审计**（重复键是运行时崩溃）
4. **符号引用检查**（新加的东西有没有调用点，避免死代码）

这些**都不能替代真机编译**。改完记得让用户在 Xcode 里跑一遍。
